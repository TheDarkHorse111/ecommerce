# Ecommerce Architecture Design

Status: approved 2026-09-07, amended 2026-09-08. Authoritative over any memory file or prior conversation.

## 1. What this is

A single-seller ecommerce backend, built as microservices in one Maven monorepo. Suliman is the seller and the owner. There is no marketplace, no second seller, ever.

The shop theme is a PC shop, but the theme is seed data only. The backend stays domain-agnostic: no domain concept becomes a table, column, or class name. Brand is an EAV attribute, not a `brand` table. Any modelling argument whose premise is "in a PC shop, X is always true" gets rejected.

The frontend is a separate, non-Java project and is out of scope here.

## 2. Standing rules

These are absolute and are not renegotiated per ticket.

### Spring annotations

`@Component`, `@Service` and `@Repository` are forbidden. `@RestController` is the only stereotype allowed, and only in the controller layer. Every other bean is declared as an `@Bean` method inside an `@Configuration` class. The purpose is that business classes stay plain Java and can be lifted out of Spring.

Spring Data JPA repository interfaces are the one exception, because Spring generates their implementations and they cannot be constructed by hand.

### Queries

No raw query text in Java. No `@Query`, no native SQL strings, no Criteria string fragments. Only Spring Data derived query methods. Raw SQL is allowed and expected inside Flyway migration files.

### Layering

```
controller  →  service  →  repository  →  jpa
```

The controller speaks Request and Response records. The service speaks models. The repository returns models and depends on the JPA repository plus the mapper. The JPA layer owns entities.

The service and the repository each have an interface plus an implementation in the same package, named `CategoryServiceImpl` and `CategoryRepositoryImpl`. There is no `impl` subpackage. The interfaces exist so that framework annotations stay on the implementation and the contract stays plain.

`@Transactional` and caching annotations live at the service level, never on the repository or the controller.

### Types

Models are Lombok classes (`@Data @NoArgsConstructor @AllArgsConstructor`), not records, unless a type is genuinely read-only. Request and Response types at the controller boundary are records.

Boundary types are named for the entity, never for the operation: `CategoryRequest` and `CategoryResponse`, never `CreateCategoryRequest` or `UpdateCategoryRequest`. One request type per entity. The operation is already named by the HTTP method and the endpoint, and per-operation records are near-identical files that have to be kept in sync by hand. A field that only applies to one operation is a nullability or validation-group question, not a reason for a second record.

No value-object wrappers. No `Money`, `Price`, `Amount`, `Sku`, `Slug`. Money is a bare `BigDecimal`. If a currency type is ever needed it is `java.util.Currency`.

Identifiers are native `uuid` columns holding UUIDv7, generated by Hibernate with `@UuidGenerator(style = UuidGenerator.Style.VERSION_7)`. The `UUID` type appears only on the entity; every layer above the JPA layer uses `String`. MapStruct converts between the two natively, so there is no UUID mapper.

Money columns are `numeric(19, 3)` and entity fields carry `@Column(precision = 19, scale = 3)`. JOD has three decimal places. Comparisons use `compareTo`, never `equals`.

Lookup methods are prefixed `find` at every layer. Mutations use verbs.

### API layer

Validation is Jakarta Bean Validation via `spring-boot-starter-validation`. Constraints live on Request records only; entities carry none. Validating the same value in two places means two places to change it and two places to disagree.

Constraints guard shape: blank, length, format, sign, range. Integrity stays in the database, so uniqueness is a 409 and never a field error.

A `@RestControllerAdvice` extending `ResponseEntityExceptionHandler` renders every Spring MVC exception as `ProblemDetail` and attaches the rejected fields to the body as a structured `errors` array. It also maps what that base class does not handle, including `DataIntegrityViolationException` to 409. Exception handling is API-layer work, so the advice is component-scanned like `@RestController`; this is consistent with the stereotype rule rather than an exception to it.

Boot can produce a `ProblemDetail` with no Java at all, by setting `spring.mvc.problemdetails.enabled` and supplying a `problemDetail.…MethodArgumentNotValidException={1}` message property. That yields one prose sentence rather than a structured `errors` array, and leaves `DataIntegrityViolationException` as a 500, so the advice is written instead and the flag stays `false`.

Custom `ConstraintValidator` implementations are `@Bean` methods in `@Configuration`, like every other non-controller bean.

OpenAPI documents are generated from the controllers and never hand-written, because a hand-maintained document is a second source of truth that drifts and is believed anyway. `@Tag`, `@Operation` and `@ApiResponse` carry only what types cannot express. Constraints feed both enforcement and the generated schema, so the two cannot disagree.

### Testing

TDD is mandatory. No class is written before a failing test for it has been seen to fail.

TDD applies to code with behaviour: a branch, a loop, validation, orchestration, arithmetic, an HTTP contract. Code with no behaviour gets no test and therefore no test-first step. That means no tests for MapStruct-generated mappers, exceptions that only extend `RuntimeException`, Lombok accessors, entity field declarations, or `@Bean` methods that just call a constructor.

Never test the framework. No test asserting that `@NotNull` rejects null, that `@Transactional` opens a transaction, or that `@Column(precision, scale)` sets a column type.

Unit tests only for now. No Testcontainers, no database, no Spring context in tests. Integration tests arrive later, once real flows exist. Repository implementation tests are in scope and assert that the JPA repository was called and that mapping happened.

Static test data lives in named constants, never repeated inline.

### Comments and scope

No Javadoc, no comment blocks. A comment that feels necessary means the code is badly written; fix the code.

Build only what was asked. No helper classes, DTOs, or configuration knobs that nobody requested.

## 3. Services

Flat at the repository root. The root `pom.xml` becomes a pure parent with a `<modules>` list, and the current root Spring Boot application (`EcommerceApplication` plus its empty `application.yaml`) is deleted.

| Module | Port | Responsibility |
| --- | --- | --- |
| `discovery-server` | 8761 | Eureka. Service registry. |
| `config-server` | 8888 | Spring Cloud Config, backed by a separate git repository. |
| `gateway` | 8080 | Spring Cloud Gateway (servlet/MVC). Routes in its own YAML. |
| `catalog-service` | 8081 | Categories, products, variants, attributes, translations. |
| `search-service` | 8082 | Meilisearch indexing and query. No database. |
| `cart-service` | 8083 | Redis only. No database. |
| `order-service` | 8084 | Orders and order lines. |
| `payment-service` | 8085 | Phase 3. Not built yet. |
| `inventory-service` | 8086 | Stock quantities. |

Keycloak runs on 8180 at its own address, in front of nothing and behind nothing. It is not routed through the gateway, so that browser redirects and issuer URLs stay stable.

### URLs

Each service is its own application and owns its own versioning.

```
/catalog/api/v1/categories/keyboards/accessories
```

The gateway matches `Path=/catalog/**` and applies `StripPrefix=1`. The controller declares `@RequestMapping("/api/v1/categories")`. The gateway stays ignorant of what any service does; it only routes on the first path segment.

Routes live in the gateway module's own YAML, under `spring.cloud.gateway.server.webmvc.routes`. That is the servlet gateway's prefix in Spring Cloud Gateway 5; `spring.cloud.gateway.mvc` is the older form and plain `spring.cloud.gateway` is the reactive one, and neither binds. Route URIs are `lb://` so that Eureka resolves the instance and no port is written down.

Routes are not in the config repository. They are wiring rather than an operational value, and a new service's route ships at the same moment as the service. This is a deliberate choice rather than a limitation: the servlet gateway does hold its config-driven routes in a refresh-scoped holder, so they would reload on a Bus refresh if they lived there.

The discovery locator stays disabled, because it generates uppercase paths such as `/CATALOG-SERVICE/**` and routes every registered application, the config server included.

The gateway validates no tokens. It forwards the `Authorization` header, and each service verifies the JWT itself.

### Configuration

The config server reads a git repository separate from this one. Layout is one shared triplet plus one triplet per application:

```
application.yaml              every service, every profile
application-local.yaml
application-prod.yaml
catalog-service.yaml
catalog-service-local.yaml
catalog-service-prod.yaml
```

`/catalog-service/local` returns the four matching files merged, most specific winning. An application gets its own triplet only when it has a key the shared files cannot carry.

Configuration lives here, not in the modules. One managed and versioned place for it, separate from the code that reads it, is the reason the config server exists at all. A module keeps only what it needs before it can fetch anything — `spring.application.name`, `spring.profiles.active`, and the config server's own address — plus `config-server`'s own settings, which cannot come from itself, and the gateway routes, for the reason given above.

Some of what lives here is also worth changing while the system is running, and that is a second benefit rather than the price of entry. Business values and operational values that turn out to be set wrong are worth a refresh. Core wiring — port, datasource, Eureka registration — takes effect on the next restart, and that is the intent rather than a limitation.

Keys that differ between profiles are limited to addresses and verbosity: datasource URL and credentials, Eureka `defaultZone`, Keycloak issuer URI, Redis, Meilisearch and Redpanda hosts, log level, SQL echo. Everything else is shared.

`prod` carries the same values as `local` except log level, which is `DEBUG` with SQL echo on locally and `INFO` with it off in production. One key is kept deliberately different because with identical files a filename typo or a broken merge is indistinguishable from success.

`spring.cloud.config.server.git.uri` points at the GitHub remote under both profiles. A filesystem path under `local` makes a push invisible to the running server, so a refresh test would pass while proving nothing.

Real production values are not committed. Secret storage is deferred to a vault.

Refresh runs over Spring Cloud Bus on Kafka. `/monitor` on the config server accepts GitHub's push payload and broadcasts a refresh scoped to the applications whose files changed; `/actuator/busrefresh` broadcasts the same event manually. Refresh rebinds `@ConfigurationProperties` beans and re-creates `@RefreshScope` beans, and `@RefreshScope` goes on `@Bean` methods.

`/actuator/busrefresh` is not routed through the gateway and is not reachable from outside the network. `/monitor` is public and verifies GitHub's `X-Hub-Signature-256` HMAC against a shared secret, rejecting anything that fails.

### Package layout

Per service, rooted at `com.thedarkhorse.<service>`:

```
config/       @Configuration classes, every bean lives here
controller/   controller + Request and Response records
service/      interface + CategoryServiceImpl, @Transactional and caching here
repository/   interface + CategoryRepositoryImpl
jpa/          CategoryEntity + CategoryJpaRepository
model/        Lombok models
mapper/       MapStruct mappers
exception/    exceptions
```

## 4. Data

Every table gets its own Flyway migration file. There is no single SQL file containing all tables.

Every business table carries `created_at`, `created_by`, `updated_at`, `updated_by`. `created_by` and `updated_by` hold the Keycloak subject as `varchar(64)`.

There is no `currency` column anywhere; the shop sells in JOD. There are no tax columns; prices are tax-inclusive.

All databases live in one Postgres container, one logical database per service.

### catalog_db

```sql
category (
  id          uuid primary key,
  parent_id   uuid null references category(id) on delete restrict,
  slug        varchar(100) not null,          -- Latin only
  path        varchar(500) not null unique,   -- materialised path, e.g. keyboards/accessories
  sort_order  int not null default 0,
  active      boolean not null default true,
  created_at, created_by, updated_at, updated_by,
  unique nulls not distinct (parent_id, slug)
)
```

`path` exists so that a subtree query is a single `like 'keyboards/%'` instead of recursion. `nulls not distinct` is what makes the unique constraint apply to root categories, whose `parent_id` is null.

```sql
translation (
  id           uuid primary key,
  entity_type  varchar(50) not null,
  entity_id    uuid not null,                 -- deliberately not a foreign key
  field        varchar(50) not null,
  language     varchar(5) not null check (language in ('ar', 'en')),
  value        text not null,
  unique (entity_type, entity_id, field, language)
)
```

One translation table serves every entity in the service. `entity_id` cannot be a foreign key because it points at several tables. `entity_type` and `language` are `varchar` with a check constraint, not Postgres enums, so that adding a language is a data change and not a migration on a type.

UI string translations are not in this table; they are JSON files per language shipped with the frontend.

```sql
product (
  id          uuid primary key,
  category_id uuid not null references category(id),
  slug        varchar(150) not null unique,
  active      boolean not null default true,
  created_at, created_by, updated_at, updated_by
)

variant (
  id         uuid primary key,
  product_id uuid not null references product(id) on delete cascade,
  sku        varchar(64) not null unique,
  price      numeric(19,3) not null,          -- tax inclusive
  images     text[] not null default '{}',    -- MinIO object keys, not URLs
  active     boolean not null default true,
  created_at, created_by, updated_at, updated_by
)
```

A product is the thing a customer shops for; a variant is the thing they actually buy and the thing that has a price and a stock count. A keyboard is a product; the ISO Arabic layout with brown switches is a variant.

`images` stores object keys such as `variants/{id}/01.webp`. Storing keys rather than URLs means the bucket, the CDN host and the signing scheme can all change without a data migration.

The EAV block is deferred until after the first increment, but the shape is settled:

```sql
attribute (
  id          uuid primary key,
  code        varchar(50) not null unique,   -- machine name: ram_capacity, switch_type
  data_type   varchar(20) not null,          -- option | text | number | boolean
  filter_type varchar(20) not null,          -- checkbox | range | toggle | none
  audit
)
attribute_option     (id, attribute_id fk, code varchar(50), audit)
category_attribute   (category_id fk, attribute_id fk, primary key (category_id, attribute_id))
variant_attribute_value (
  variant_id   uuid references variant(id) on delete cascade,
  attribute_id uuid references attribute(id),
  option_id    uuid null references attribute_option(id),
  value_text   text null,
  value_number numeric null,
  value_bool   boolean null,
  primary key (variant_id, attribute_id)
)
```

`category_attribute` declares which attributes a category's items may have. `variant_attribute_value` holds what a specific variant's value actually is. Attribute names and option labels are translated through the `translation` table.

`data_type` and `filter_type` are deliberately separate columns, because storage and presentation do not line up. `data_type` says which value column holds the answer and how it compares. `filter_type` says what control the customer sees. The same `number` can be a tickbox list or a slider:

```
code           data_type  filter_type
ram_capacity   number     checkbox     -- 16 GB, 32 GB, 128 GB as tickboxes
switch_type    option     checkbox
weight         number     range        -- min-max slider
hot_swappable  boolean    toggle
warranty_years number     none         -- printed as a spec, not filterable
```

A `number` attribute rendered as `checkbox` needs no `attribute_option` rows. The choices come from Meilisearch's facet distribution, which returns the distinct values present in the current result set with a count for each. A `range` attribute reads facet stats instead, which gives the min and max that become the two ends of the slider. So `filter_type` decides which of those two Meilisearch outputs the frontend reads.

Units live in the translated label, not in a column and never in the stored value. `ram_capacity` stores a bare `16` and is indexed as a JSON number, so `ram_capacity 16 TO 128` still works; the label reads "Capacity (GB)". Storing `"16 GB"` as text would kill range filtering and is forbidden.

Price is not an EAV attribute. It is a real column on `variant`. Price, category and in-stock are built-in filters that the search service always indexes and the frontend always knows how to draw. The `attribute` table governs only the filters that vary by category.

Known limitation: `category_attribute` cannot carry a per-category `filterable` flag that Meilisearch will honour, because Meilisearch's filterable-attributes set is index-global. Filterability is decided per attribute, once, for the whole index. `filter_type = none` is the switch for it, and it applies everywhere the attribute is used.

```sql
outbox (
  id             uuid primary key,
  aggregate_type varchar(50) not null,
  aggregate_id   uuid not null,
  event_type     varchar(100) not null,
  payload        jsonb not null,
  created_at     timestamptz not null,
  published_at   timestamptz null
)
create index on outbox (created_at) where published_at is null;
```

The partial index is what keeps the poller's query cheap as the table grows, because it only indexes rows that have not been published.

### inventory_db

```sql
inventory (
  variant_id uuid primary key,               -- soft reference to catalog
  quantity   int not null check (quantity >= 0),
  restock_at date null,
  updated_at, updated_by
)
```

No `version` column. Locking is pessimistic, using `@Lock(LockModeType.PESSIMISTIC_WRITE)`. The reasoning is that stock is written almost entirely by the system during checkout, so contention is real rather than rare, and a caller that loses an optimistic race would have to be told to try again by hand — which is worse than waiting briefly for the row.

Out-of-stock items stay visible in the catalog. They sort last and display an out-of-stock status.

Plus an `outbox` table with the same shape as above. Inventory publishes an event only when availability crosses zero, not on every quantity change.

### order_db

```sql
orders (
  id            uuid primary key,
  order_number  bigint not null unique,      -- sequence backed, human facing
  customer_id   varchar(64) not null,        -- Keycloak subject
  status        varchar(30) not null,
  subtotal      numeric(19,3) not null,
  shipping_fee  numeric(19,3) not null,
  total         numeric(19,3) not null,
  ship_name     varchar(150) not null,
  ship_phone    varchar(30)  not null,
  ship_line1    varchar(255) not null,
  ship_city     varchar(100) not null,
  ship_area     varchar(100) not null,
  placed_at     timestamptz not null,
  updated_at    timestamptz not null
);
create index on orders (customer_id, placed_at desc);
```

The shipping address is copied onto the order rather than referenced, because an order is a historical record. If the customer edits their saved address next year, last year's order must still show where the parcel actually went.

`order_number` is separate from `id` because a customer reading a UUID down the phone is unusable.

```sql
order_line (
  id         uuid primary key,
  order_id   uuid not null references orders(id) on delete cascade,
  variant_id uuid not null,                  -- soft reference to catalog
  sku        varchar(64)  not null,
  name_ar    varchar(255) not null,
  name_en    varchar(255) not null,
  unit_price numeric(19,3) not null,
  quantity   int not null check (quantity > 0),
  line_total numeric(19,3) not null
);
create index on order_line (order_id);
```

SKU, both names and the unit price are copied for the same reason: the order shows what was bought at the price it was bought for, even after the catalog changes or the variant is deleted.

Plus an `outbox` table. `customer_address` is deferred.

### payment_db — phase 3, not built

```sql
payment (
  id           uuid primary key,
  order_id     uuid not null,
  provider     varchar(50) not null,
  provider_ref varchar(255) not null,
  amount       numeric(19,3) not null,
  status       varchar(30) not null,
  created_at   timestamptz not null
)

payment_event (
  id                uuid primary key,
  payment_id        uuid not null references payment(id),
  provider_event_id varchar(255) not null unique,
  type              varchar(100) not null,
  payload           jsonb not null,
  received_at       timestamptz not null
)
```

`provider` exists because `provider_ref` is meaningless without knowing whose reference it is, webhook payload shapes differ per provider, and reconciliation is done per provider. A second Jordanian payment method such as Zain Cash or Orange Money is plausible.

The unique constraint on `provider_event_id` is what makes a redelivered webhook a no-op instead of six confirmation emails.

Cash on delivery ships first, because it is the dominant payment method in Jordan and because no Jordanian payment provider will issue sandbox credentials without commercial registration.

### cart-service

Redis only, no Postgres. One hash per customer, keyed `cart:{keycloakSubject}`, mapping variant id to quantity. AOF persistence is on and the key carries a long TTL.

Guest carts stay in the browser. A cart is only worth storing server-side once the customer is logged in, because the point is that a cart added to on a phone is still there on a laptop.

### search-service

No database of its own. It reads from catalog and writes to Meilisearch.

Arabic needs explicit normalisation, because Charabia does not strip the `ال` definite article — measured on Meilisearch 1.53, where `جوال` matched and `الجوال` returned zero hits. Normalisation strips diacritics and Tatweel, folds Alef, Yeh, Taa-Marbuta and Waw-Hamza, and strips the `ال`, `وال`, `بال`, `كال`, `فال` and `لل` prefixes when at least three characters remain. It is applied both at index time and to the incoming query.

## 5. Messaging

Redpanda is the broker. It was chosen substantially for its learning value, and that was said out loud: the CDC and index-rebuild arguments for a log were both investigated and withdrawn.

Events carry facts, never commands. If an event name reads as an instruction, such as `ReserveStock`, it belongs in orchestration and not on the log.

Every service that publishes writes to its own `outbox` table inside the same transaction as the business change, and a poller publishes from there. That is what stops a service from committing a row and then failing to publish, or publishing and then failing to commit.

## 6. Infrastructure

Each service owns its own Docker Compose file. The shared Postgres container hosts one database per service.

Authentication is OAuth2 authorization code flow with PKCE against Keycloak. Services verify JWTs against Keycloak's JWKS endpoint and hold no session state. Customer profile fields beyond what Keycloak stores are not duplicated into a local user table.

Errors are returned as RFC 7807 `ProblemDetail`.

Verified dependency pins: Spring Boot 4.1.0, Java 25, `spring-cloud-dependencies` 2025.1.2 exactly, Eureka server 5.0.2, the servlet/MVC gateway rather than the reactive one, MapStruct 1.6.3, Lombok 1.18.42. The annotation processor path lists Lombok before MapStruct.

springdoc is 3.1.1; the 3.x line is the Spring Boot 4 line and 2.x stayed on Boot 3. `spring-boot-starter-validation` resolves Hibernate Validator 9.1.0.Final. Spring Cloud Bus is 5.0.2 and Config Monitor 5.0.4, both from the same train. Bus needs its own Kafka binder configuration, separate from the binder carrying domain events, because the Kafka starter forces byte-array serializers onto any binder it shares (`spring-cloud-bus` #267, #268).

### Root POM

The root POM has no `<parent>`. Spring Boot and Spring Cloud are imported as BOMs, which keeps the parent slot free and inherits no plugin configuration.

Because `spring-boot-starter-parent` is not the parent, nothing sets `-parameters`, so `maven.compiler.parameters` is set explicitly in the root properties. Without it javac emits `arg0`, `arg1` for record components, springdoc cannot match a constraint annotation on a canonical constructor parameter to its JSON property, and no field is marked required in the generated schema.

Root `pluginManagement` declares `spring-boot-maven-plugin` with its `repackage` execution and `maven-compiler-plugin` with the annotation processor path. Each runnable module declares `spring-boot-maven-plugin` with no version or configuration; the root declares neither.

Every plugin carries an explicit version, because a BOM import supplies `dependencyManagement` only and no `pluginManagement` is inherited. `maven-compiler-plugin` is pinned at 3.16.0; Maven 3.9.16 otherwise falls back to 3.15.0.

### Static analysis

Error Prone 2.50.0 runs as a javac plugin during compilation, so a finding fails the build rather than filling a report nobody reads. `error_prone_core` sits on the same `annotationProcessorPaths` as Lombok, the binding and MapStruct, because setting that path disables processor discovery on the classpath and anything missing from it stops running without saying so. A root `lombok.config` sets `lombok.addLombokGeneratedAnnotation = true` so that Error Prone does not report on generated accessors.

A root `.mvn/jvm.config` carries the `--add-exports` and `--add-opens` flags that Error Prone documents for JDK 16 and above. `maven-compiler-plugin` compiles in Maven's own JVM rather than forking, so that JVM is the one whose `jdk.compiler` internals Error Prone needs open; without the file the compiler dies with `IllegalAccessError` on `com.sun.tools.javac.api.BasicJavacTask` before analysing anything. Forking the compiler and passing the same flags `-J`-prefixed is the alternative, and is rejected because it spawns a javac process per module for no gain.

Severity is per bug pattern, not global. `SelfAssignment` is an error and fails the build, `ReferenceEquality` is a warning and does not. Findings are not promoted wholesale with `-Werror`, because the warning tier is where Error Prone puts checks with real false-positive rates.

There is no separate lint step. `mvn verify` is the single gate.

## 7. Build order

1. Restructure the repository into a parent POM plus flat modules, and delete the root Spring Boot application.
2. Stand up `discovery-server`, `config-server` and `gateway`.
3. `catalog-service` with `category` and `translation`. A category with no name is unusable, so translation ships in the same increment.
4. The rest of catalog: `product`, `variant`, then the EAV block.
5. `inventory-service`, then `order-service`, then `search-service` and `cart-service`.
6. Phase 3: `payment-service`.

Each increment is a superpowers implementation plan, and each phase within it puts the failing test before the code.

## 8. Deferred, and deliberately so

- `customer_address` in order_db.
- Whether attribute values need splitting into product-level descriptive values and variant-level defining values. One table on variant is enough today.
- Integration tests and Testcontainers.
- Card payments, blocked until commercial registration exists.
- OpenTelemetry.
- A secret vault, chosen once there is somewhere to deploy.
- ArchUnit rules enforcing the standing rules — the annotation ban, the layering, the `find` prefix, the Request and Response naming. Deferred deliberately: Error Prone cannot see any of these, so the rules are held by review for now, and ArchUnit gets added if review starts finding drift.
- Aggregating every service's OpenAPI document behind the gateway.
