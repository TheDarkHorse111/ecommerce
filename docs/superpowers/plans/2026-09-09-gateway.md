# gateway Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stand up `gateway`, the servlet/MVC Spring Cloud Gateway on port 8080, registered in Eureka and routing the `/catalog` prefix to `lb://catalog-service` with the first path segment stripped.

**Architecture:** One Maven module, `gateway/`, parented by the root POM and listed in its `<modules>` beside `discovery-server`. Two runtime dependencies — `spring-cloud-starter-gateway-server-webmvc` for the servlet gateway and `spring-cloud-starter-netflix-eureka-client`, which both registers the gateway and supplies the load balancer that resolves `lb://`. One Java class carrying `@SpringBootApplication`, one `@RestControllerAdvice` that renders an unresolvable upstream as a `ProblemDetail` with the load balancer's own status, and one `application.yaml` holding the port, the application name and the route table. There is no service, repository or JPA layer, so only the controller-layer half of the layering rule has anything to bite on.

**Tech Stack:** Java 25 (Amazon Corretto 25.0.4.1), Apache Maven 3.9.16, Spring Boot 4.1.0, Spring Framework 7.0.8, Spring Cloud 2025.1.2, `spring-cloud-starter-gateway-server-webmvc` 5.0.2, `spring-cloud-starter-netflix-eureka-client` 5.0.2, `spring-cloud-starter-loadbalancer` 5.0.2 (transitive), Error Prone 2.50.0, maven-compiler-plugin 3.16.0, JUnit 5 and AssertJ via `spring-boot-starter-test`.

**Spec:** `docs/superpowers/specs/2026-09-05-ecommerce-architecture-design.md` (section 3 service table, the "URLs" subsection, section 6 "Root POM" and "Static analysis", section 7 step 2). Issue #12 is the specification for this increment. Issue #10, already merged, is its stated dependency and is planned in `docs/superpowers/plans/2026-09-09-discovery-server.md`; issue #1 is planned in `docs/superpowers/plans/2026-09-09-repository-restructure-parent-pom.md`.

## Global Constraints

Copied from `CLAUDE.md` and the spec. Every task's requirements implicitly include this section.

- **Build gate:** `mvn -B clean verify` from the repository root is the only gate. There is no separate lint step. Error Prone runs during compilation, so a finding fails the build.
- **Port:** 8080. **Package root:** `com.thedarkhorse.gateway`. **Module directory:** `gateway/`, flat at the repository root. **Eureka application name:** `gateway`.
- **Route prefix:** `spring.cloud.gateway.server.webmvc.routes`. Not `spring.cloud.gateway.mvc.routes`, not `spring.cloud.gateway.routes`. Verified below — the two wrong prefixes bind nothing and fail silently.
- **Routes live in this module's own YAML**, never in the config repository. One route per service, matching the first path segment and stripping it. `lb://` URIs only, so no port is written down.
- **Annotations.** `@Component`, `@Service` and `@Repository` are forbidden. `@RestController` and `@RestControllerAdvice` are the only stereotypes, controller layer only. Every other bean would be an `@Bean` method in an `@Configuration` class; this module needs none. `@SpringBootApplication` is not a stereotype and is not covered by the ban.
- **Layering.** `controller → service → repository → jpa`. This module has a controller layer only — one `@RestControllerAdvice` — and no service, repository or jpa package.
- **Types.** No value-object wrappers. Boundary types are records named for the entity. This module has no Request or Response type: the gateway proxies bytes and never deserialises a body.
- **Naming.** Lookups are prefixed `find` at every layer. Mutations use verbs.
- **TDD.** No class is written before a failing test for it has been seen to fail. TDD applies to code with behaviour. The advice in Task 2 has behaviour — it maps an exception to a status — so it gets a JUnit test written first. `GatewayApplication` has none, so per `CLAUDE.md` it gets no test. Every other red step below is a command whose observed failure is recorded verbatim. **Never test the framework** — no test asserting that `Path=` matches or that `StripPrefix` strips, and the spec forbids a Spring context in tests outright, so no `@SpringBootTest`.
- **Comments.** None. No Javadoc, no comment blocks, and none in `pom.xml`, `application.yaml` or any properties file. Rationale lives in the spec and in this plan.
- **Scope.** Build only what issue #12 asks for. In particular do **not** add an actuator dependency, `spring-boot-starter-oauth2-resource-server`, a `TokenRelay` filter, a circuit breaker, a retry filter, `eureka.client.service-url.defaultZone`, `eureka.instance.*`, a `spring.cloud.gateway.discovery.locator.enabled` key, a Dockerfile, a Compose file, or a `README`. See "Deliberate omissions" for the four the issue text will tempt you into.
- **Every plugin carries an explicit version** — but this module declares only `spring-boot-maven-plugin`, with no version and no configuration, because the root `pluginManagement` supplies both. That is the pattern the spec fixes for every runnable module, and `discovery-server/pom.xml` is the precedent already in the tree.
- **Conventional Commits** with `gateway` as the scope, one commit per completed red-green cycle, every commit green, each carrying a `Refs #12` footer. No `Co-Authored-By` trailer, no generated-with footer.
- **Pull request** title ends `(#12)`; body ends `Closes #12`. Merge with rebase, never squash.

## Verified Findings

Every claim issue #12 makes about tool behaviour was executed in this repository before planning on top of it, using a throwaway module at `.scratch/gateway-probe/` parented to the real root `pom.xml` by `<relativePath>` and never listed in `<modules>`, with the real `discovery-server` jar running alongside it on 8761. The probe was deleted afterwards.

**One claim in the issue turned out to be false and one turned out to be moot.** Read "Where the issue is wrong" before Task 2.

### Confirmed

1. **`spring-cloud-starter-gateway-server-webmvc` is the servlet gateway artifact in this train, at 5.0.2.** `mvn dependency:tree` on the probe:

   ```
   +- org.springframework.cloud:spring-cloud-starter-gateway-server-webmvc:jar:5.0.2:compile
   |  +- org.springframework.cloud:spring-cloud-gateway-server-webmvc:jar:5.0.2:compile
   |  |  +- org.springframework.boot:spring-boot-restclient:jar:4.1.0:compile
   |  |  \- org.springframework.boot:spring-boot-starter-validation:jar:4.1.0:compile
   |  \- org.springframework.boot:spring-boot-starter-web:jar:4.1.0:compile
   \- org.springframework.cloud:spring-cloud-starter-netflix-eureka-client:jar:5.0.2:compile
      +- com.netflix.eureka:eureka-client:jar:2.0.6:compile
      \- org.springframework.cloud:spring-cloud-starter-loadbalancer:jar:5.0.2:compile
   ```

   No version is written in the module POM; `spring-cloud-dependencies` 2025.1.2 supplies both. Tomcat and Spring MVC arrive transitively — this is the servlet flavour, and no reactive stack is on the classpath.

2. **The property prefix in the issue is right.** `META-INF/spring-configuration-metadata.json` inside `spring-cloud-gateway-server-webmvc-5.0.2.jar` declares exactly one group:

   ```json
   { "name": "spring.cloud.gateway.server.webmvc",
     "type": "org.springframework.cloud.gateway.server.mvc.config.GatewayMvcProperties" }
   ```

   and the routes property is `spring.cloud.gateway.server.webmvc.routes`. Neither `spring.cloud.gateway.mvc` nor plain `spring.cloud.gateway` appears anywhere in the file.

3. **The wrong prefix fails silently, which is why Task 2's red is what it is.** The probe was run with the route table under the reactive `spring.cloud.gateway.routes`. The application started normally — no warning, no bind failure — and `GET /catalog/api/v1/x` returned:

   ```
   HTTP 404
   Content-Type: application/json
   {"timestamp":"...","status":404,"error":"Not Found","path":"/catalog/api/v1/x"}
   ```

   Boot ignores unknown configuration keys, so a typo in the prefix is indistinguishable from having written no routes at all.

4. **Filter and predicate names are bound at context refresh, not at request time.** Writing `StripPrefixx=1` instead of `StripPrefix=1` does not start and 404 later; it kills startup:

   ```
   Error creating bean with name 'gatewayCompositeRouterFunction': ... Factory method
   'routerFunctionHolderSupplier' threw exception with message: Unable to find operation interface
   org.springframework.web.servlet.function.HandlerFilterFunction for stripPrefixx with args {_genkey_0=1}
   ```

   So a gateway that starts at all has genuinely bound `StripPrefix=1`. That is the strongest evidence available for the filter while issue #14's catalog instance does not exist.

5. **The gateway registers in Eureka, under `GATEWAY`.** With `discovery-server` running on 8761 and no `eureka.client` block at all in the gateway, `GET /eureka/apps` 45 seconds after startup:

   ```json
   {"applications":{"versions__delta":"1","apps__hashcode":"UP_1_","application":[
     {"name":"GATEWAY","instance":[{"app":"GATEWAY","status":"UP",
       "port":{"$":8080,"@enabled":"true"},"vipAddress":"gateway", ... }]}]}}
   ```

   The Eureka client's default `defaultZone` is `http://localhost:8761/eureka/`, so the key is not written down. `"port":{"$":8080}` is the registry corroborating the port.

6. **An unknown prefix returns 404 with no stack trace in the body**, both before and after the advice of Task 2 is added:

   ```
   HTTP 404
   Content-Type: application/json
   {"timestamp":"...","status":404,"error":"Not Found","path":"/nope/api/v1/x"}
   ```

7. **`Authorization` is forwarded.** The only header filter on by default that removes anything is `RemoveHopByHopRequestHeadersFilter`, and its list, read out of the class constant pool with `javap -c`, is `connection`, `keep-alive`, `transfer-encoding`, `te`, `trailer`, `proxy-authorization`, `proxy-authenticate`, `x-application-context`, `upgrade`. `Authorization` is not on it; `proxy-authorization` is a different header. No token validation runs, because no resource-server starter is on the classpath.

### Where the issue is wrong

**A. FALSE — "returns 503 while no catalog instance is registered". Out of the box it returns 500.**

The claim was tested with exactly the YAML the issue prints. `GET /catalog/api/v1/x` returned:

```
HTTP 500
Content-Type: application/json
{"timestamp":"...","status":500,"error":"Internal Server Error","path":"/catalog/api/v1/x"}
```

and the gateway logged a full stack trace to the console:

```
ERROR ... o.a.c.c.C.[.[.[/].[dispatcherServlet] : Servlet.service() for servlet [dispatcherServlet] ...
threw exception [Request processing failed: org.springframework.web.client.HttpServerErrorException:
503 Unable to find instance for catalog-service] with root cause

org.springframework.web.client.HttpServerErrorException: 503 Unable to find instance for catalog-service
	at org.springframework.cloud.gateway.server.mvc.filter.LoadBalancerFilterFunctions.lambda$lb$0(LoadBalancerFilterFunctions.java:92)
```

The route matches and the load balancer does decide 503, but it signals it by throwing `HttpServerErrorException`. `javap` on `spring-web-7.0.8.jar` shows that class extends `HttpStatusCodeException` → `RestClientResponseException` → `RestClientException` and implements neither `ErrorResponse` nor `ResponseStatusException`, so Spring MVC has no way to read 503 off it and falls through to 500. Nothing in `spring-configuration-metadata.json` for the webmvc gateway configures this — the whole file is fifteen `enabled` flags, the `routes` and `routes-map` properties, `streaming-*`, `trusted-proxies`, `use-framework-retry-filter`, `forwarded-by-enabled` and the `x-forwarded-*` block. There is no knob.

The criterion is therefore met by writing the mapping, which is what Task 2's second cycle does. With a `@RestControllerAdvice` that returns `ProblemDetail.forStatusAndDetail(exception.getStatusCode(), exception.getStatusText())`:

```
HTTP 503
Content-Type: application/problem+json
{"detail":"Unable to find instance for catalog-service","instance":"/catalog/api/v1/x","status":503,"title":"Service Unavailable"}
```

That also satisfies the spec's "Errors are returned as RFC 7807 `ProblemDetail`", and it silences the console stack trace: after the advice was added the count of `Servlet.service() for servlet` lines in the gateway log was **0**.

**B. MOOT — "The discovery locator stays disabled." There is no discovery locator in the servlet gateway to disable.**

`unzip -l spring-cloud-gateway-server-webmvc-5.0.2.jar` returns no `DiscoveryClientRouteDefinitionLocator` and no class with `Locator` in its name at all; the only route-related classes are `RouteProperties`, `RouterFunctionHolderFactory` and `GatewayMvcPropertiesBeanDefinitionRegistrar$RouterFunctionHolder`. `spring.cloud.gateway.discovery.locator.enabled` is a reactive-gateway key and is absent from this module's configuration metadata. Setting it would bind to nothing and `CLAUDE.md` forbids configuration knobs nobody requested, so **the key is not written**.

The behaviour the issue wants is nevertheless real and is asserted directly: with `GATEWAY` registered in Eureka, `GET /GATEWAY/anything` returned `HTTP 404`, not a proxied response. Task 2 keeps that check.

Incidentally this confirms the spec's other remark about the servlet gateway: the config-driven routes really do live in a refresh-scoped `RouterFunctionHolder`, visible in the bean name `scopedTarget.gatewayRouterFunctionHolder` in finding 4's stack trace.

### Three things the issue does not say

**C. `spring-cloud-starter-netflix-eureka-client` is mandatory twice over, and the second reason breaks startup.**

The issue's Design block names neither the gateway starter nor the Eureka client. Both consequences were measured.

Without the Eureka client and with no routes, the gateway starts happily and simply never appears in the registry — `Tomcat started on port 8080`, `Started GatewayApplication in 2.119 seconds`, and `GET /eureka/apps` after a 45-second settle is `{"applications":{"versions__delta":"1","apps__hashcode":"","application":[]}}`. That is Task 1's red.

Without the Eureka client and **with** the `lb://` route, the application does not start at all, because the load balancer that arrives transitively with the Eureka client is what registers the `lb` scheme:

```
Error creating bean with name 'routerFunctionMapping' ... Error creating bean with name
'gatewayCompositeRouterFunction': Error creating bean with name 'scopedTarget.gatewayRouterFunctionHolder':
Failed to instantiate [ ...GatewayMvcPropertiesBeanDefinitionRegistrar$RouterFunctionHolder]:
Factory method 'routerFunctionHolderSupplier' threw exception with message:
Unable to find HandlerFunction for scheme: lb
```

Exit code 1. This is why Task 1 adds the dependency and Task 2 adds the route, in that order and not the other way round.

**D. `spring.application.name` is required here, unlike in `discovery-server`.**

With the Eureka client present but no name set, registration succeeds under the wrong name:

```json
{"applications":{ ... "application":[{"name":"UNKNOWN","instance":[{"app":"UNKNOWN",
  "instanceId":"...:8080","vipAddress":"unknown", ... }]}]}}
```

Acceptance criterion 1 is "appears in the Eureka registry", and an entry called `UNKNOWN` cannot be told apart from any other unnamed application, so the criterion would be vacuous. `discovery-server` deliberately omits the key because it registers with nobody; the gateway is the opposite case. That is the second red inside Task 1.

**E. `GET /eureka/apps` is served from a response cache that refreshes every 30 seconds.** Measured during issue #10 and unchanged here: an instance the server has already logged as registered can still be absent from two consecutive polls. The staleness runs one way — a registry that is filling up still reads as empty — so a check taken at t+2s passes on a correctly configured gateway **and** on a broken one. **Every `/eureka/apps` check in this plan waits at least 45 seconds after startup**, which is what the settle argument to `Probe.java` is for.

### Deliberate omissions

- **No `spring.cloud.gateway.discovery.locator.enabled: false`.** Finding B: there is nothing to disable, and the key does not bind.
- **No `eureka.client.service-url.defaultZone`.** Finding 5: the client's default is already `http://localhost:8761/eureka/`, the issue does not ask for the key, and the spec puts per-profile `defaultZone` in the config repository rather than here.
- **No security starter and no `TokenRelay` filter.** The issue says the gateway validates no token and forwards `Authorization`; finding 7 shows that is what an unconfigured gateway already does. Adding a resource-server starter would make it validate tokens, which is the opposite of what was asked.
- **No actuator.** Eureka's registration advertises `/actuator/health` and `/actuator/info` in the instance metadata whether or not those endpoints exist. Nothing in issue #12 reads them, and the registry entry is `"status":"UP"` regardless, because `EurekaClientAutoConfiguration` falls back to the client's own status when no health check is configured. Do not add the dependency to make those URLs real.

- [ ] **Step 1: Write the failing test**

Two pieces. First the HTTP client, because the allowlist has none. Create `.scratch/Probe.java` exactly as below. It retries the connection for up to two minutes so it can be launched before a server is up, then sleeps `settleSeconds` before the request it actually reports — that sleep is what makes an `/eureka/apps` check meaningful rather than vacuous (finding E).

```java
import java.io.IOException;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.time.Duration;

public class Probe {

    public static void main(String[] args) throws Exception {
        String url = args[0];
        String accept = args.length > 1 ? args[1] : "*/*";
        long settleSeconds = args.length > 2 ? Long.parseLong(args[2]) : 0L;

        HttpClient client = HttpClient.newHttpClient();
        HttpRequest request = HttpRequest.newBuilder(URI.create(url))
                .header("Accept", accept)
                .timeout(Duration.ofSeconds(30))
                .build();

        long deadline = System.currentTimeMillis() + 120_000L;
        while (true) {
            try {
                client.send(request, HttpResponse.BodyHandlers.discarding());
                break;
            } catch (IOException e) {
                if (System.currentTimeMillis() > deadline) {
                    throw e;
                }
                Thread.sleep(1000L);
            }
        }

        Thread.sleep(settleSeconds * 1000L);

        HttpResponse<String> response = client.send(request, HttpResponse.BodyHandlers.ofString());
        System.out.println("HTTP " + response.statusCode());
        System.out.println("Content-Type: " + response.headers().firstValue("Content-Type").orElse("none"));
        System.out.println(response.body());
    }
}
```

`Probe.java` lives under `.scratch/` and is never committed. It carries no comments, consistent with the standing rule, and it is a throwaway harness rather than production code, so it needs no test of its own.

```java
package com.thedarkhorse.gateway.controller;

import org.springframework.http.ProblemDetail;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.client.HttpServerErrorException;

@RestControllerAdvice
public class GatewayExceptionHandler {

        return ProblemDetail.forStatusAndDetail(exception.getStatusCode(), exception.getStatusText());
    }
}
```

## Pull request

Title: `feat(gateway): add servlet gateway routing the catalog prefix (#12)`

Body lists each of the four acceptance criteria with the command and the output that verified it, marks criterion 4 as deferred to #14 by the issue itself, and ends with `Closes #12`. Merge with rebase, never squash, so the three per-cycle commits survive.

The body must also carry the two places the issue's Design block did not survive contact with the tool, since a reviewer comparing the YAML to the issue will otherwise flag both:

- **The issue says 503; the gateway returns 500 unless you write the mapping.** `LoadBalancerFilterFunctions` signals an unresolvable `lb://` by throwing `HttpServerErrorException`, which implements neither `ErrorResponse` nor `ResponseStatusException`, so Spring MVC renders 500 and logs a stack trace. There is no configuration property for it — the whole `spring.cloud.gateway.server.webmvc` metadata is `enabled` flags, `routes`, `routes-map`, `streaming-*`, `trusted-proxies`, `use-framework-retry-filter` and `x-forwarded-*`. `GatewayExceptionHandler` is what makes the criterion true, and it returns the exception's own status rather than a hard-coded 503.
- **`spring.cloud.gateway.discovery.locator.enabled: false` is not in the YAML, and that is not an oversight.** The servlet gateway 5.0.2 jar ships no `DiscoveryClientRouteDefinitionLocator` and no locator key in its configuration metadata; the property is reactive-only and would bind to nothing. The behaviour is asserted instead: with `GATEWAY` registered in Eureka, `GET /GATEWAY/anything` returns 404.

And the two additions the issue does not mention but which the criteria require: `spring-cloud-starter-netflix-eureka-client`, without which the registry stays empty and — once the `lb://` route exists — the context fails to refresh with `Unable to find HandlerFunction for scheme: lb`; and `spring.application.name: gateway`, without which the registration lands under `UNKNOWN` and criterion 1 cannot distinguish the gateway from any other unnamed application.
